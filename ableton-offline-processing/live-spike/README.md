## Offline verification

From `ableton-offline-processing/live-spike`, run the dependency-free mock-host tests with Node 24.16 or later.

```powershell
node --test round-trip.test.mjs
```

Seven tests passed on standalone Node `26.13.0` and on the candidate beta's bundled Node binary `24.22.1` run as a standalone CLI. Tests cover isolated clip validation, WAV metadata and hash measurement, use of the host-returned import path, positive modal confirmation, cancellation, stale Set rejection and cleanup of a new empty track after clip creation fails. The SDK calls are mocked in these tests. The fixture is stereo PCM16 at 48 kHz, 96,000 frames, 384,044 bytes. The Live render must be measured separately.

## Official SDK build and disposable Set procedure

1. Extract the original beta.1 archive outside the repository. With its documented Node 24 toolchain, follow the bundled Quick Start to build its `context-menu` example in a separate workspace. This checks the official SDK, CLI and bundler independently.
2. Generate a second project with beta.1's project generator. Use its documented installation and build steps. Replace the generated `src/extension.ts` with [the spike entry](src/extension.ts) and add [the spike module](src/round-trip.ts) next to it. Point the generated developer configuration at the explicitly chosen side-by-side **Live 12 Beta** Extension Host. Check the resolved host path before invoking any run command.
3. After approval to use a disposable Set, open the confirmed beta and verify its exact authorized edition and version in **About Live** and its **Settings → Extensions** panel. Enable Developer Mode there and use the archive's documented development launch commands for the official example and then the spike. Retrieve activation diagnostics from the beta's `ExtensionHost.txt`. Keep any SDK package, `.ablx` bundle, generated WAV or logs containing personal details outside version control.
4. From the spike directory, generate a new local fixture WAV with `node fixture.mjs <new-path-outside-repository.wav>`. At 120 BPM, create a fresh disposable Set with one stereo fixture clip starting at beat 8 (bar 3 in 4/4) and ending at beat 12. Use an otherwise empty unmuted audio track with no take lanes, devices, fades, warp, loop or automation. Turn off Auto-Warp for the fixture and verify the beta's Record File Type is WAV. Record the input's SHA-256 with `Get-FileHash -Algorithm SHA256 <fixture.wav>`.
5. Right-click the Arrangement clip and choose **AOPX · Test isolated clip round-trip**. Check the console for the reported clip range, WAV channel count, sample rate, format tag/bit depth, frame count, bytes and hash. Cancel once during progress and once in the confirmation dialog, then confirm one import. A valid import uses Live's returned project-media path and creates a separate Arrangement track. Compare the original and output clips at the requested start/length, and recheck the fixture SHA-256 and original Set track/clip metadata.
6. Compare the actual rendered audio content with the fixture at a matched render sample rate. The fixture has a roughly 440 Hz burst on the left during seconds 0.25–0.75 and a roughly 660 Hz burst on the right during seconds 1.00–1.50. The nominal lengths are 96,000 frames at 48 kHz or `2 × render sample rate` at another rate. Confirm the channel, order, amplitude and quiet gaps, and record any boundary fade, rate conversion or level discrepancy. A file hash measures integrity and does not establish sample equality across different WAV encodings/headers.
7. For separate host characterization, use variants of the bundled `strip-silence` pre-FX example on copies of the disposable fixture Set. Change one condition at a time (other playable material on the track in the range, take-lane comp, clip fades, track/clip automation, then tempo changes). Compare against the isolated baseline and log actual frames, timestamps and signal differences. The spike intentionally rejects extra Arrangement clips and take lanes, so these broader cases use a separate test. Record the requested 420×220 modal's actual dimensions, native controls, close result and ability to cancel while the host render is pending.

## Integration constraints

- `renderPreFxAudio` receives an AudioTrack and Arrangement beat range. It acquires the track's pre-effects signal. The spike reads the returned WAV inside Extension temp space and passes it to `importIntoProject`. It uses the returned import path for `createAudioClip`. The documented host call lacks an abort argument, so cancellation checks discard a completed render before any Set write. The host could finish that operation after the user clicks cancel. [Beta.1 archive review](../SDK_ARCHIVE_REVIEW_BETA_1.md)
- The spike uses an unwarped, unlooped fixture and explicitly requests an unwarped new clip. It captures basic loop/warp metadata for diagnostics. A full track-range render already bakes audible clip behaviour, so applying original media-relative markers and warp/loop transforms to it can change the result again. A separate warped/looped fixture must establish placement and valid metadata-copy rules. The SDK documents creation-time loop settings and writable warp state/mode. Its listed warp markers are read-only. [Beta.1 archive review](../SDK_ARCHIVE_REVIEW_BETA_1.md)
- Extension storage and temp space are the documented file roots. The spike leaves host-managed imported files to Live, including a copy that might remain if import succeeds and later clip creation fails. Creating a track and creating a clip are dependent asynchronous calls; the spike tries to remove only its own empty output track if creation fails. Undo grouping, rollback behaviour and imported-media retention require host verification. Child processes must obey the host sandbox, and the current route uses none. [Beta.1 archive review](../SDK_ARCHIVE_REVIEW_BETA_1.md)
- The evidence supports a single modal result using `close_and_send`, followed by Node-side processing with the separate progress dialog. Actual Webview lifetime, dimensions and theme support require host checks. Built-in device insertion, pre-FX track rendering and the public beta task model do not establish post-FX rendering or third-party VST3/AU/ARA hosting.
